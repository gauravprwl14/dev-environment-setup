# contextsync — Docs-Only Navigation Design
**Date**: 2026-03-26
**Status**: Approved for implementation

---

## Problem

The current contextsync skill places CONTEXT.md files throughout the source tree, mirroring the codebase structure. This has two failure modes:

1. **Source tree pollution** — CONTEXT.md files mixed into `src/`, `lib/`, and module folders confuse developers and IDE tooling, and add noise to git history.
2. **No bootstrap** — CLAUDE.md (always loaded first) has no explicit pointer to the documentation system. Claude must guess where the docs live, making navigation brittle across projects.

---

## Solution Overview

Two changes, working together:

1. **Docs-only default** — All CONTEXT.md files live exclusively inside a `docs/` folder per app, structured in three layers. The source tree is never touched.
2. **Explicit bridge in CLAUDE.md** — A standardized `## Context Navigation` section in CLAUDE.md tells Claude exactly where the docs system starts. Auto-generated by `contextsync setup`, so no manual work required.

---

## The Docs Structure

All CONTEXT.md files live inside a `docs/` folder. Three layers, fixed:

```
docs/
  CONTEXT.md                    ← Layer 1: domain router ("what domains exist?")
  features/
    CONTEXT.md                  ← Layer 2: feature router ("which feature answers this?")
    FEAT-orders.md              ← Layer 3: content (feature guides)
    FEAT-auth.md
    FEAT-payments.md
  engineering/
    CONTEXT.md                  ← Layer 2: engineering router
    architecture.md             ← Layer 3: content
  infrastructure/
    CONTEXT.md                  ← Layer 2: infra router
    deployment.md               ← Layer 3: content
```

**Layer rules:**
- Layer 1 (`docs/CONTEXT.md`): maps domain questions to domain subfolders. ≤ 100 lines.
- Layer 2 (`docs/{domain}/CONTEXT.md`): maps specific questions to content files within that domain. ≤ 100 lines.
- Layer 3 (`docs/{domain}/*.md`): actual content files. No size limit.

**Layer 3 naming conventions:**
- Feature guides use the `FEAT-{kebab-case}.md` prefix (defined in the pre-existing `references/feature-guide-spec.md` — not modified by this spec).
- All other content files use plain descriptive names (e.g., `architecture.md`, `deployment.md`). No prefix required outside the `features/` domain.

**Source tree rule:** The source tree (`src/`, `lib/`, etc.) is never touched. No CONTEXT.md files outside the `docs/` folder(s) defined in `## Context Navigation`.

**Scaling:** When a Layer 2 CONTEXT.md approaches 100 lines, split the domain into sub-domains:

```
docs/features/
  CONTEXT.md                    ← routes to sub-domains only
  account-management/
    CONTEXT.md
    FEAT-registration.md
    FEAT-profile.md
  payments/
    CONTEXT.md
    FEAT-checkout.md
    FEAT-refunds.md
```

The 100-line limit drives healthy decomposition without requiring upfront planning.

## The CLAUDE.md Bridge

### Single app

```markdown
## Context Navigation
docs/CONTEXT.md
```

### Monorepo (multiple entry points)

```markdown
## Context Navigation
web: apps/web/docs/CONTEXT.md
api: apps/api/docs/CONTEXT.md
shared: packages/shared/docs/CONTEXT.md
```

Labels are user-defined strings (e.g., `web`, `api`, `shared`). The skill reads both formats:
- No label on the path line → single app, use the path directly.
- Lines in `label: path` format → monorepo; the skill picks the relevant entry point per task using the routing logic below.

**Missing section:** If `## Context Navigation` is absent from CLAUDE.md, the skill halts any docs task and emits a warning: *"No `## Context Navigation` found in CLAUDE.md. Run `contextsync setup` to configure this."* The skill does not attempt to guess or fall back to a default path.

---

## Monorepo Navigation Routing

When multiple labeled entry points exist, the skill picks the right one per task:

**App root derivation:** For each labeled entry point (e.g., `web: apps/web/docs/CONTEXT.md`), the app root prefix is derived by removing the `/docs/CONTEXT.md` suffix. Example: `apps/web/docs/CONTEXT.md` → app root prefix `apps/web`. This derived prefix is used for file path matching below.

```
Task arrives
│
├─ File paths mentioned in task? (e.g. apps/web/src/...)
│    └─ Derive app root prefix from each entry point (remove /docs/CONTEXT.md suffix)
│         └─ Check if mentioned path starts with that prefix
│              └─ Match found → use that entry point
│
├─ App label name mentioned in task? (e.g. "in the API", "the web app")
│    └─ Fuzzy-match against label names from ## Context Navigation
│         └─ Match found → use that entry point
│
└─ No clear signal
     └─ Ask the user once:
        "Which app does this task relate to? [label1 | label2 | ...]"
        (labels shown are the actual label names from ## Context Navigation)
```

One question maximum. Never guess silently.

## `contextsync setup` — New Command

A one-time interactive setup command. Idempotent — safe to re-run if the project changes.

### Flow

```
Step 1 — Check CLAUDE.md
  ├─ CLAUDE.md does not exist at project root
  │    → Halt: "CLAUDE.md not found. Create CLAUDE.md at the project root before running setup."
  ├─ CLAUDE.md exists, ## Context Navigation present
  │    → Do NOT exit. Continue to Step 3 to check if structure is complete.
  │      (Setup is a "ensure complete" command — it fills in any missing stubs
  │       even when navigation is already configured. It never overwrites.)
  └─ CLAUDE.md exists, ## Context Navigation missing → continue all steps.

Step 2 — Ask: "Is this a monorepo with multiple apps? (yes/no)"
  ├─ Answer not "yes" or "no" → re-ask once.
  │    Still invalid → halt: "Invalid input. Re-run contextsync setup and enter yes or no."
  ├─ No (single app)
  │    └─ Ask: "Where is your docs folder? (default: docs/)"
  │         → normalize: strip leading/trailing slashes (e.g. "/docs/" → "docs")
  │         → store as DOCS_ROOT
  └─ Yes (monorepo)
       └─ Ask: "List your apps as name:path pairs, one per line.
                Path is the app root (e.g. web:apps/web).
                Enter a blank line when done."
            → read lines until blank line
            → parse each non-blank line as "label:app_root"
            → normalize each app_root: strip leading/trailing slashes
            → store as list of {label, app_root} pairs
            → derive DOCS_ROOT per app as "{app_root}/docs"

Step 3 — For each DOCS_ROOT (one for single app, one per app for monorepo):
  ├─ DOCS_ROOT exists AND has at least one immediate subfolder
  │    └─ Infer domain names from immediate subfolders
  │         └─ Confirm with user: "Found these domains: [list]. Add or remove any? (enter to confirm)"
  └─ DOCS_ROOT missing, OR exists with no subfolders (including the case where only loose .md files are present)
       └─ Ask: "What domains do you want to organize docs by?
                Enter comma-separated names (e.g. features, engineering, infrastructure)"

Step 4 — Scaffold missing structure (per DOCS_ROOT)
  ├─ DOCS_ROOT/CONTEXT.md missing → create Layer 1 stub
  └─ DOCS_ROOT/{domain}/CONTEXT.md missing per confirmed domain → create Layer 2 stub
  Note: Never overwrite any CONTEXT.md that already exists. Skip and report.

Step 5 — Write ## Context Navigation block into CLAUDE.md
  ├─ Single app → write:
  │    ## Context Navigation
  │    {DOCS_ROOT}/CONTEXT.md
  └─ Monorepo → write one labeled line per app:
       ## Context Navigation
       {label}: {app_root}/docs/CONTEXT.md

Step 6 — Report summary
  └─ List every file created, every file skipped (already existed), and whether CLAUDE.md was modified.
```

### Idempotency rules

- Never overwrite an existing CONTEXT.md — only create stubs for files that are missing.
- Setup is re-runnable at any time. It fills in whatever is missing and skips whatever already exists.
- If `## Context Navigation` already exists in CLAUDE.md: skip Step 2 path questions (infer entry points from the existing block), proceed to Step 3 to check for missing stubs, and skip Step 5 (no CLAUDE.md write needed). Report what was created vs. skipped.
- If `## Context Navigation` is absent: run all steps, write the block at Step 5.
- Never modify CLAUDE.md for any purpose other than writing the `## Context Navigation` block.

**Setup creates Layer 1 and Layer 2 stubs only.** Layer 3 content files (feature guides, architecture docs, etc.) are never created by setup. They are created manually or by the contextsync skill when documenting individual features.

## `references/setup-guide.md` — New Reference File

This file is loaded by the skill when executing the setup task. It contains:

**Sections:**
1. **When to run setup** — first-time project setup; after adding a new app to a monorepo; if `## Context Navigation` was manually removed.
2. **Domain naming guidance** — recommended domain names for common project types (e.g., `features`, `engineering`, `infrastructure` for backend services; `components`, `hooks`, `pages` for frontend apps); rule that domain names should match the questions developers ask, not the source tree structure.
3. **Monorepo walkthrough** — step-by-step example of running setup on a two-app monorepo (`apps/web` + `apps/api`), showing exact prompts, answers, and resulting CLAUDE.md output.
4. **Partial structure handling** — what to do when some CONTEXT.md files already exist. Matches the idempotency rules above.
5. **Verifying the setup** — how to confirm the bridge is working: read CLAUDE.md, confirm `## Context Navigation` is present, navigate to the entry path and confirm Layer 1 CONTEXT.md exists.

## Navigation Protocol Update (SKILL.md)

The mandatory first step before any task:

```
Bootstrap (run before every task):
  1. Read CLAUDE.md → find ## Context Navigation
     ├─ Section absent
     │    → Warn: "No '## Context Navigation' found in CLAUDE.md. Run contextsync setup."
     │    → Halt. Do not proceed with the task.
     ├─ Single entry (no label)
     │    → Use path directly as Layer 1 entry point
     └─ Multiple labeled entries (label: path format)
          a. Infer app from task context (file paths, label name mentions)
          b. If match found → use that entry point
          c. If ambiguous → ask once: "Which app? [label1 | label2 | ...]"
             (show actual labels from ## Context Navigation)
  2. From selected entry point, run the 3-layer chain as normal.
```

The rest of the navigation protocol (3-layer chain, quality gates, exception handling) is unchanged.

## Task Decision Tree Update (SKILL.md)

Add two new branches at the top of the decision tree:

```
Incoming task
│
├─ "setup" / "initialize docs" / "contextsync setup"
│    └─ LOAD references/setup-guide.md → RUN setup procedure
│
├─ ## Context Navigation missing from CLAUDE.md AND task is not "setup"
│    └─ WARN: "No '## Context Navigation' found in CLAUDE.md. Run contextsync setup."
│         → Do not proceed with any docs task.
│
└─ [all existing branches unchanged]
```

## What Does NOT Change

- Quality gates G1–G6.
- Feature guide spec (6 sections, `FEAT-` naming convention).
- Agent handoff schemas.
- Lint script (the `LINT_DOCS_ROOT` env var already defaults to `docs` — no code change needed).
- Source-mirror mode — deferred, not in scope for this spec.

## Acceptance Criteria

- [ ] `contextsync setup` halts with a clear message if CLAUDE.md does not exist at the project root
- [ ] `contextsync setup` asks "single app or monorepo?" before asking any other question (Step 1 check is not a user-facing question)
- [ ] `contextsync setup` asks for domain names when `docs/` does not exist or is empty
- [ ] `contextsync setup` infers and confirms domain names from existing subfolders when `docs/` is present
- [ ] `contextsync setup` creates Layer 1 and Layer 2 CONTEXT.md stubs for all missing files
- [ ] `contextsync setup` writes a valid `## Context Navigation` block to CLAUDE.md
- [ ] `contextsync setup` (monorepo) writes one labeled line per app to `## Context Navigation`, using `{label}: {app_root}/docs/CONTEXT.md` format
- [ ] `contextsync setup` is re-runnable — when `## Context Navigation` already exists, it skips to stub-repair (Steps 3–4), creates any missing stubs, and skips Step 5 (no CLAUDE.md re-write)
- [ ] `contextsync setup` never overwrites existing CONTEXT.md stubs regardless of run state
- [ ] Skill navigates correctly via `docs/CONTEXT.md` entry point on a single-app docs-only project
- [ ] Skill picks the correct entry point in a monorepo when file paths in the task match an app root prefix
- [ ] Skill picks the correct entry point in a monorepo when the app label name is mentioned in the task
- [ ] Skill asks exactly once when entry point is ambiguous in a monorepo, showing actual label names
- [ ] Skill warns and halts (does not proceed) when `## Context Navigation` is absent and the task is not "setup"
- [ ] `contextsync setup` (monorepo) normalizes trailing slashes in user-provided app root paths before writing CLAUDE.md
- [ ] Source tree (`src/`, `lib/`, etc.) is never modified by any skill operation
- [ ] All existing quality gates (G1–G6) continue to pass on a docs-only project
